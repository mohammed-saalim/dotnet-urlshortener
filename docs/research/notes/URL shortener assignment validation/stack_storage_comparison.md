# Stack and Storage Comparison for a 2-3 Day .NET URL Shortener Prototype

Research date: 2026-10-10. All "VERIFIED" items were read from the linked page on this date via Microsoft Learn MCP / WebFetch. "UNVERIFIED" items come from training knowledge or were not confirmed by a primary source in this pass and must be checked before being written into the ADR as fact.

Scope reminder: engineer is a .NET/C# API developer on Windows 11, no employer resources, may or may not have an Azure subscription; reviewer must run the prototype end-to-end locally.

## Key Question 1: Application stack (.NET 8 vs .NET 10, Minimal API vs controllers, vs Node/Go/Python) and what "production-grade" .NET looks like to interviewers

### Takeaway
.NET 8 reaches end of support on 10 Nov 2026 (one month after this research date), and .NET 10 is the current LTS (supported to Nov 2028), so .NET 10 is the only defensible target for a "production-grade" project submitted in Oct 2026. Microsoft's own guidance recommends Minimal APIs for new projects; controllers are justified only for model-binding extensibility, advanced MVC validation, OData, or team familiarity.

### Cited Findings
- VERIFIED: .NET 10 is LTS, released 11 Nov 2025, end of support 14 Nov 2028. .NET 9 is STS, end of support 10 Nov 2026. .NET 8 is LTS, end of support 10 Nov 2026. "LTS releases get free support and patches for three years." — [.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)
- VERIFIED: "ASP.NET Core provides two approaches for building HTTP APIs: Minimal APIs and controller-based APIs. For new projects, we recommend using Minimal APIs." Reasons listed: simpler syntax, better performance ("reduced overhead compared to controllers"), easier testing, modern approach. — [APIs overview](https://learn.microsoft.com/aspnet/core/fundamentals/apis?view=aspnetcore-10.0)
- VERIFIED: "Consider controller-based APIs if you need: Model binding extensibility (IModelBinderProvider, IModelBinder); Advanced validation features (IModelValidator); Application parts or the application model; OData support. Most of these features can be implemented in Minimal APIs with custom solutions, but controllers provide them out of the box." — [APIs overview, Choosing between approaches](https://learn.microsoft.com/aspnet/core/fundamentals/apis?view=aspnetcore-10.0#choosing-between-approaches)
- VERIFIED: Controllers "may be preferred for: Large applications with complex business logic; Teams familiar with the MVC pattern; Applications requiring specific MVC features." — [APIs overview, Controller-based APIs](https://learn.microsoft.com/aspnet/core/fundamentals/apis?view=aspnetcore-10.0#controller-based-apis---alternative-approach)
- VERIFIED: Error-handling doc says Minimal APIs should "Configure problem details using AddProblemDetails() for consistent error responses"; controller-based error handling is suggested for "Complex model validation scenarios; Centralized exception handling across multiple controllers; Fine-grained control over error response formatting; Integration with MVC features like filters and conventions." — [Handle errors in ASP.NET Core APIs](https://learn.microsoft.com/aspnet/core/fundamentals/error-handling-api?view=aspnetcore-10.0#additional-error-handling-features)
- VERIFIED: ProblemDetails pattern for Minimal APIs: `builder.Services.AddProblemDetails(); app.UseExceptionHandler(); app.UseStatusCodePages();` generates RFC problem-details responses "for all HTTP client and server error responses that don't have body content yet". `DefaultProblemDetailsWriter` supports `application/json`, `application/problem+json` and wildcard Accept types only. — [Handle errors in ASP.NET Core APIs, Problem details](https://learn.microsoft.com/aspnet/core/fundamentals/error-handling-api?view=aspnetcore-10.0#problem-details)
- VERIFIED: Built-in OpenAPI document generation since .NET 9 via `Microsoft.AspNetCore.OpenApi` (`AddOpenApi()` + `MapOpenApi()`, document served at `openapi/v1.json`). The template restricts the OpenAPI endpoint to the Development environment. .NET 10 defaults to OpenAPI 3.1; build-time generation is available via `Microsoft.Extensions.ApiDescription.Server`. — [What's new in ASP.NET Core 9, OpenAPI](https://learn.microsoft.com/aspnet/core/release-notes/aspnetcore-9.0?view=aspnetcore-10.0#openapi); [Generate OpenAPI documents](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/aspnetcore-openapi?view=aspnetcore-10.0); [OpenAPI overview](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/overview?view=aspnetcore-10.0)
- VERIFIED: HybridCache (`Microsoft.Extensions.Caching.Hybrid`) is documented in the .NET 10 ASP.NET Core docs as a shipped library with stampede protection, two-level (L1 in-memory + optional L2 IDistributedCache) caching, tag-based invalidation and configurable serialization. It supports .NET Framework 4.7.2 / .NET Standard 2.0 and up. — [HybridCache library in ASP.NET Core](https://learn.microsoft.com/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0); [Caching in .NET, Hybrid caching](https://learn.microsoft.com/dotnet/core/extensions/caching#hybrid-caching)
- UNVERIFIED (not fetched in this pass): Health checks (`AddHealthChecks()` + `MapHealthChecks("/health")`), Options pattern (`IOptions<T>` with `ValidateDataAnnotations().ValidateOnStart()`), and OpenTelemetry (`OpenTelemetry.Extensions.Hosting` + ASP.NET Core / HttpClient / EF Core instrumentation, exported via OTLP) are the standard "production-grade" building blocks in Microsoft's documentation and in the .NET Aspire ServiceDefaults project template. Confirm against learn.microsoft.com/aspnet/core/host-and-deploy/health-checks and learn.microsoft.com/dotnet/core/diagnostics/observability-with-otel before citing in the ADR.
- UNVERIFIED (comparison with other ecosystems; no sources fetched): Node/TypeScript (Fastify or NestJS), Go (net/http or chi/echo), and Python (FastAPI) can all build a URL shortener in 2-3 days with similar effort. None was fetched or benchmarked here. The reason to pick .NET is not raw capability but that the candidate is being evaluated as a .NET engineer, that EF Core gives a provider-switch story (SQLite local, SQL Server/Azure SQL/PostgreSQL in prod), and that Azure hosting/observability integrations (Container Apps, App Service, Application Insights) are first-party for .NET.

### Inferences
- Target `net10.0` and say so in the ADR with the support dates above. Choosing .NET 8 in October 2026 would be defensible only if the reviewer's environment mandates it, and it would need an explicit note that it goes out of support within weeks.
- Use Minimal APIs organized by feature (endpoint groups via `MapGroup`, `TypedResults`, endpoint filters for validation), not a single Program.cs. This matches Microsoft's "recommended for new projects" stance and avoids the common interviewer criticism that Minimal API samples are unstructured. Do NOT use Minimal APIs if the brief requires OData, heavy custom model binders, or if the reviewing team explicitly standardizes on controllers; in that case controllers are the lower-risk choice and the docs explicitly list those cases.
- "Production-grade" checklist that is directly backed by the Microsoft docs above: `AddProblemDetails` + `UseExceptionHandler`, `AddOpenApi`/`MapOpenApi` (Development-only exposure), HybridCache or IMemoryCache for the redirect hot path, plus the UNVERIFIED-but-standard items (health checks, Options validation, OpenTelemetry, structured logging). Record each as a one-line decision in the ADR.
- When NOT to use .NET for this problem: if the deployment target is edge/serverless-KV only (Cloudflare Workers, see Sink below), or if the reviewer's stack is explicitly non-.NET. Otherwise the ecosystem comparison is a wash for a 2-3 day prototype.

### Gaps
- No primary source fetched for Health Checks, Options pattern, or OpenTelemetry pages (budget); flagged UNVERIFIED above.
- No head-to-head benchmark or feature comparison with Fastify/NestJS/Go/FastAPI was fetched; the comparison is inference only.
- Interviewer expectations are inherently anecdotal; no survey or primary source exists. The checklist above is derived from Microsoft's own templates and docs rather than from interviewer statements.

## Key Question 2: Storage comparison for key -> URL lookup, hot read path, write-once records, append-only click analytics

### Takeaway
For a reviewer-runnable, subscription-optional prototype, the strongest combination is: relational store via EF Core (SQL Server Linux container or PostgreSQL container on Docker Desktop for the "real" path; SQLite for zero-dependency fallback and tests), with Azure SQL free offer (100,000 vCore-seconds + 32 GB per month, 10 databases per subscription, no time limit) as the cloud target. Cosmos DB and Table Storage have good free tiers and emulators but weaker uniqueness/EF Core stories for a case-sensitive short-code key; Redis is a cache, not a primary store, for this prototype.

### Cited Findings

Azure SQL Database (free offer)
- VERIFIED: "For each database, you get 100,000 vCore seconds, 32 GB of data, and 32 GB of backup storage free per month for the lifetime of your subscription. Each Azure subscription allows you to create up to 10 General Purpose databases." The offer "is available regardless of your Azure subscription type" (the old offer required an Azure Free subscription). — [Deploy Azure SQL Database for free](https://learn.microsoft.com/azure/azure-sql/database/free-offer?view=azuresql)
- VERIFIED: Two behaviours when the monthly limit is hit: "Auto-pause the database until next month" (max 4 vCores, 32 GB, PITR limited to 7 days, backup storage free) or "Continue using database for additional charges" at standard General Purpose serverless rates; once converted to paid you "can't revert". — [Deploy Azure SQL Database for free, Monthly free limits](https://learn.microsoft.com/azure/azure-sql/database/free-offer?view=azuresql#monthly-free-limits)
- VERIFIED: "The database is free forever, with monthly limits. There's no time limit." The free amount "doesn't come with a service level agreement (SLA) and is recommended primarily for development and proof-of-concept scenarios." — [Azure SQL Database free offer FAQ](https://learn.microsoft.com/azure/azure-sql/database/free-offer-faq?view=azuresql)
- VERIFIED: Serverless bills vCore-seconds while the database is online, not CPU %. Any open connection (SSMS, app connection pools, health probes) prevents auto-pause and burns credits; one user exhausted 100,000 vCore-seconds in 2 days with ~0.3% CPU. Microsoft recommends monitoring the "Free amount remaining" metric and creating an alert at 10,000 seconds. — [Microsoft Q&A answer](https://learn.microsoft.com/answers/a/12568728); [Free offer, Monitor and track](https://learn.microsoft.com/azure/azure-sql/database/free-offer?view=azuresql#monitor-and-track-service-usage)
- VERIFIED: Free SQL Managed Instance also exists (720 vCore-hours/month for 12 months, 64 GB), but it is a 12-month offer and a heavier product; not relevant for this prototype. — [Try Azure SQL Managed Instance for free](https://learn.microsoft.com/azure/azure-sql/managed-instance/free-offer?view=azuresql)

- VERIFIED: SQL Server container images (`mcr.microsoft.com/mssql/server`) are Linux containers, "supported only on Linux hosts running on Intel and AMD x86-64 CPUs"; emulation (Rosetta 2, Prism, QEMU) is "not tested or supported". Windows containers for SQL Server "aren't covered by support". — [Deploy and connect to SQL Server Linux containers](https://learn.microsoft.com/sql/linux/containers/deploy?view=sql-server-ver17)
- VERIFIED: Requirements: at least 2 GB RAM and 2 GB disk for the container; "SQL Server needs at least 2 GB of memory to start a Linux-based container" and "uses approximately 80% of the memory available to the container" by default. The VS Code mssql extension's local container feature "Requires Docker Desktop (or equivalent)", "Only supports Linux-based SQL Server containers (SQL Server 2017 and later)", "No support for Podman". — [Quickstart: Run SQL Server Linux container images with Docker](https://learn.microsoft.com/sql/linux/install-upgrade/quickstart-install-docker?view=sql-server-ver17#prerequisites); [Local SQL Server container (mssql extension)](https://learn.microsoft.com/sql/tools/visual-studio-code-extensions/mssql/mssql-local-container?view=sql-server-ver17#limitations)

- VERIFIED: With an Azure free account, Flexible Server is free "for 12 months" with monthly limits of "750 hours of Burstable B1MS instance" and "32 GB storage and 32 GB backup storage". — [Use an Azure free account to try Azure Database for PostgreSQL for free](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-deploy-on-azure-free-account)

- VERIFIED: PostgreSQL unique indexes: "When an index is declared unique, multiple table rows with equal indexed values are not allowed." - UNVERIFIED: Azure Database for PostgreSQL Flexible Server has no always-free tier after the 12-month free-account window; the cheapest B1ms is on the order of USD 12-15/month if left running. Check azure.microsoft.com/pricing/details/postgresql before quoting.

SQLite
- VERIFIED: EF Core SQLite provider limitations: no schemas, no sequences, no database-generated concurrency tokens; `DateTimeOffset`, `decimal`, `TimeSpan`, `ulong` are stored but comparison/ordering requires client evaluation; many migration operations are performed via table rebuild; no idempotent migration scripts. — [SQLite EF Core Database Provider Limitations](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/limitations)

### Inferences
- Comparison matrix for the ADR (L = local runnability without subscription; E = emulator fidelity; U = unique constraint for case-sensitive short code; EF = EF Core support; $ = free tier Oct 2026; S = scalability story):
  - SQL Server container + Azure SQL free: L needs Docker Desktop + 2 GB RAM; E = real engine, highest fidelity; U = unique index with explicit `_CS_AS` or `_BIN2` collation (see Q3); EF = first-party, migrations full; $ = always-free 100k vCore-s + 32 GB, 10 DBs, no card beyond the Azure account itself; S = serverless -> provisioned -> Hyperscale narrative, read replicas. Best overall fit for a .NET candidate.
  - PostgreSQL container + Flexible Server: L light container; E = real engine; U = unique index, case-sensitive by default; EF = Npgsql, excellent; $ = 12-month free B1ms only, then paid; S = strong, but cloud free tier is time-limited.
  - SQLite: L zero-dependency (file); E = n/a, it IS the engine; U = unique index, BINARY default is case-sensitive; EF = good but with the limitations above; $ = free; S = none (single file, single writer) — good for tests and fallback, bad as the "production design" story.
  - Cosmos DB: L needs Windows installer or Docker (vNext is NoSQL-only, gateway-only, no auth); E = partial; U = unique key policy per partition, immutable after creation, EF ignores constraints in the model; EF = usable but migration-free and recently broken-changed; $ = 1000 RU/s + 25 GB lifetime; S = excellent story but overkill and mismatched for a 2-3 day relational-shaped problem.
  - Table Storage: L Azurite (npm/Docker/VS); E = good for Table; U = PK+RK uniqueness (409 on insert conflict) is natural: PartitionKey = shard of code, RowKey = code; EF = none; $ = cheap, Storage is in the free-account 12-month list and pennies after; S = massive scale for point lookups, poor for ad-hoc analytics queries. Credible alternative if the engineer wants to mirror AzUrlShortener, but weaker interview narrative for "EF Core / relational design" skills.
  - Redis: primary store would need persistence config and a durability argument; as L1/L2 cache it is the standard story. For a 2-3 day prototype, in-process cache is sufficient (see Q4).
- The Azure SQL free offer's biggest operational trap for a demo is auto-pause being blocked by open connections (health probes, connection pools, SSMS), which can exhaust the month's credits in days. If the API runs on Container Apps with health probes hitting the DB, document this and either make the health check not touch the DB or accept paid mode.
- Hot read path: with any relational store, a unique index on the short code makes the redirect a single index seek; cache in front (Q4) removes the DB from the hot path entirely for popular links.

### Gaps
- Exact Oct 2026 prices for Azure Managed Redis smallest SKU, PostgreSQL B1ms, Table Storage transactions, and Cosmos RU overage were not fetched; pricing pages require live lookup.
- Azure SQL Database (single database) default collation when created via portal/CLI without specifying one was not found verbatim in this pass (MI default and LocalDB default are verified as `SQL_Latin1_General_CP1_CI_AS`; Fabric SQL database default is also `SQL_Latin1_General_CP1_CI_AS`). Treat Azure SQL DB default as UNVERIFIED but almost certainly the same CI collation; the ADR should set collation explicitly regardless.

## Key Question 3: Provider-switch pattern pitfalls (SQLite local, SQL Server/Azure SQL prod) under EF Core, and collation/case sensitivity for Base62 short codes

### Takeaway
SQL Server and Azure SQL default to a case-insensitive collation (`SQL_Latin1_General_CP1_CI_AS` for en-US / LocalDB / Managed Instance), so a plain unique index on a Base62 `ShortCode` column would treat `abc` and `ABC` as duplicates and silently shrink the keyspace; PostgreSQL and SQLite are case-sensitive by default. Fix it in the model with `.UseCollation("Latin1_General_100_BIN2")` or a `_CS_AS` collation on the column, and be explicit that SQLite-vs-SQL Server differences (concurrency tokens, decimal/DateTimeOffset ordering, migration rebuilds) mean "runs on both" is not the same as "same migrations on both".

### Cited Findings
- VERIFIED: "while some databases are case-sensitive by default (e.g. Sqlite, PostgreSQL), others are case-insensitive (SQL Server, MySQL)." "the default server-level collation in SQL Server for the 'English (United States)' machine locale is SQL_Latin1_General_CP1_CI_AS, which is a case-insensitive, accent-sensitive collation." — [EF Core: Collations and Case Sensitivity](https://learn.microsoft.com/ef/core/miscellaneous/collations-and-case-sensitivity)
- VERIFIED: Database-level: `modelBuilder.UseCollation("SQL_Latin1_General_CP1_CS_AS");` Column-level: `modelBuilder.Entity<Customer>().Property(c => c.Name).UseCollation("...");` Query-level `EF.Functions.Collate(...)` exists but "Specifying an explicit collation in a query will generally prevent that query from using an index defined on that column". "It is always preferable to define the collation at the column (or database) level." — [EF Core: Collations and Case Sensitivity](https://learn.microsoft.com/ef/core/miscellaneous/collations-and-case-sensitivity#database-collation)
- VERIFIED: SQL Server collation suffixes: `_CS` = case-sensitive ("If this option isn't selected, the collation is case-insensitive"), `_AS` = accent-sensitive, `_KS`, `_WS`. — [Collation and Unicode support, Collation terms](https://learn.microsoft.com/sql/relational-databases/collations/collation-and-unicode-support?view=sql-server-ver17#collation-terms)
- VERIFIED: "In Azure SQL Database, there's no server collation, so each database has a collation for data and a collation for the catalog ... The CATALOG_COLLATION is set upon creation and can't be changed." Catalog collation allowed values in ARM: `DATABASE_DEFAULT` or `SQL_Latin1_General_CP1_CI_AS`. — [Collation and Unicode support](https://learn.microsoft.com/sql/relational-databases/collations/collation-and-unicode-support?view=sql-server-ver17#collation-terms); [Microsoft.Sql servers/databases ARM](https://learn.microsoft.com/azure/templates/microsoft.sql/2017-03-01-preview/servers/databases#property-values)
- VERIFIED: Azure SQL Managed Instance default server collation is `SQL_Latin1_General_CP1_CI_AS`; LocalDB is fixed at `SQL_Latin1_General_CP1_CI_AS`. — [Set or change the server collation](https://learn.microsoft.com/sql/relational-databases/collations/set-or-change-the-server-collation?view=sql-server-ver17)
- VERIFIED: Mixing collations causes errors like "Cannot resolve collation conflict between 'Latin1_General_CS_AS' and 'Greek_CI_AS' in equal to operation" when comparing columns; comparison operators, `LIKE`, `IN`, `UNION` are collation-sensitive. — [Collation precedence](https://learn.microsoft.com/sql/t-sql/statements/collation-precedence-transact-sql?view=sql-server-ver17)
- VERIFIED: SQLite default collation BINARY uses `memcmp()` (case-sensitive, byte-wise); NOCASE folds ASCII only. — [SQLite Datatypes](https://www.sqlite.org/datatype3.html)
- VERIFIED: "PostgreSQL is a case-sensitive database by default"; case-insensitive options are `citext` (does not handle accents, cannot mix CS/CI on the same column) or nondeterministic ICU collations, which Npgsql notes work "quite well" only on recent versions such as PostgreSQL 18. — [Npgsql EF Core: Collations and Case Sensitivity](https://www.npgsql.org/efcore/misc/collations-and-case-sensitivity.html)
- VERIFIED: EF Core SQLite provider does not support "Database-generated concurrency tokens"; `decimal`, `DateTimeOffset`, `TimeSpan`, `ulong` support only equality server-side; `AlterColumn`, `AddUniqueConstraint`, `DropColumn`, `RenameIndex` etc. are done via table rebuild; no idempotent migration scripts. — [SQLite EF Core Provider Limitations](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/limitations)
- VERIFIED: Npgsql concurrency tokens use PostgreSQL's hidden `xmin` system column (`uint` property with `[Timestamp]` / `.IsRowVersion()`); PostgreSQL "lacks auto-updating columns like SQL Server's rowversion", and the approach is PostgreSQL-specific and not portable. — [Npgsql EF Core: Concurrency tokens](https://www.npgsql.org/efcore/modeling/concurrency.html)
- VERIFIED: EF Core 10 adds named default constraints for SQL Server (`HasDefaultValueSql("GETDATE()", "DF_Post_CreatedDate")`, `UseNamedDefaultConstraints()`), with a warning that enabling it renames every default constraint in the next migration. — [What's New in EF Core 10](https://learn.microsoft.com/ef/core/what-is-new/ef-core-10.0/whatsnew#azure-sql-and-sql-server)
- UNVERIFIED: `Latin1_General_100_BIN2` is the collation Microsoft recommends for new binary-ordinal comparisons (BIN2 compares Unicode code points; BIN has legacy quirks on the first character). Using a binary collation on the short-code column gives case-sensitive, accent-sensitive, culture-independent equality and the fastest index comparisons. Confirm on learn.microsoft.com/sql/relational-databases/collations before quoting.
- UNVERIFIED: `varchar(N)` with an ASCII-only Base62 alphabet (rather than `nvarchar`) halves index key size on SQL Server; EF Core maps `string` to `nvarchar(max)` by default unless `.IsUnicode(false).HasMaxLength(N)` is set.

### Inferences
- For a Base62 short code the ADR should state: column `ShortCode varchar(10) NOT NULL` (or `HasMaxLength(10).IsUnicode(false)`), unique index, and `.UseCollation("Latin1_General_100_BIN2")` (or `SQL_Latin1_General_CP1_CS_AS`) on SQL Server. On PostgreSQL and SQLite the default already enforces case-sensitive uniqueness; `UseCollation` with a SQL Server collation name will fail on those providers, so the collation call must be provider-conditional (e.g. `if (Database.IsSqlServer())` in `OnModelCreating`, or separate `IEntityTypeConfiguration` per provider).
- Alternatively, sidestep the collation problem entirely by using a case-insensitive alphabet (Base36 or Base32/Crockford) and lower-casing on input. This loses keyspace (36^7 = 78 billion vs 62^7 = 3.5 trillion) but removes a whole class of production incidents (users retyping codes from screenshots, case-folding proxies). Worth recording as the rejected alternative.
- Migrations: do not share one migrations folder between SQLite and SQL Server. EF Core migrations are provider-specific; either generate separate migration assemblies per provider, or use SQLite only via `EnsureCreated()` for tests and keep migrations for SQL Server/PostgreSQL only. The SQLite rebuild behaviour and lack of idempotent scripts make it a poor target for the "real" migration story.
- Concurrency tokens: `rowversion` (SQL Server) vs `xmin` (PostgreSQL) vs application-managed `Guid`/`long` version (works everywhere, including SQLite). For write-once link records, optimistic concurrency is barely needed; for click counters, prefer an append-only clicks table or atomic `UPDATE ... SET Count = Count + 1` over a tracked entity with a concurrency token.
- Type mapping: avoid `decimal` and `DateTimeOffset` in entities if SQLite must sort/compare them; store UTC `DateTime` for `CreatedAt`/`ExpiresAt` (also recommended by the SQLite limitations page).

### Gaps
- No primary source fetched for the recommended BIN2 collation name or for EF Core's default `nvarchar(max)` mapping (flagged UNVERIFIED).
- Azure SQL Database single-database default data collation not fetched verbatim (see Q2 gaps).

## Key Question 4: Is a cache layer justified in a 2-3 day prototype? IMemoryCache vs Redis vs HybridCache

### Takeaway
Yes, a cache on the redirect read path is cheap and is the clearest "I understand the hot path" signal, but it should be in-process (IMemoryCache or HybridCache with no L2) for the prototype; Redis should be documented as the L2 upgrade for multi-replica deployments, not provisioned, given the Azure Cache for Redis retirement and the absence of a free managed Redis tier.

### Cited Findings
- VERIFIED: HybridCache "By default ... uses MemoryCache for its primary cache storage. Cache entries are stored in-process, so each server has a separate cache ... For secondary out-of-process storage, such as Redis, SQL Server, or Postgres, HybridCache uses the configured IDistributedCache implementation, if any. But even without an IDistributedCache implementation, the HybridCache service still provides in-process caching and stampede protection." — [HybridCache library in ASP.NET Core](https://learn.microsoft.com/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0#cache-storage)
- VERIFIED: Microsoft's own guidance: "For single-server applications with simple caching needs, in-memory caching might be sufficient. For multi-server applications without the need for stampede protection or tag-based invalidation, consider distributed caching." Use HybridCache when you need L1+L2 in a multi-server environment, stampede protection, a simplified API, or tag-based invalidation. — [Caching in .NET, When to use HybridCache](https://learn.microsoft.com/dotnet/core/extensions/caching#hybrid-caching)
- VERIFIED: Stampede protection "doesn't extend to other HybridCache instances, even if they use the same distributed cache"; invalidation by key/tag affects the local server and L2 but "the in-memory cache in other servers isn't affected". — [HybridCache library](https://learn.microsoft.com/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0#cache-storage)
- VERIFIED: HybridCache can be registered with one call (`builder.Services.AddHybridCache()`) and used via `cache.GetOrCreateAsync(key, factory)`; immutable sealed types annotated `[ImmutableObject(true)]` avoid per-call deserialization. — [What's new in ASP.NET Core 9, HybridCache](https://learn.microsoft.com/aspnet/core/release-notes/aspnetcore-9.0?view=aspnetcore-10.0#miscellaneous)
- VERIFIED: Azure Cache for Redis Basic/Standard/Premium retire 30 Sep 2028; Azure Managed Redis is the replacement with a non-HA dev/test option without SLA. — [Retirement FAQ](https://learn.microsoft.com/azure/azure-cache-for-redis/retirement-faq)
- VERIFIED: Container Apps "When a revision is scaled to zero replicas, no resource consumption charges are incurred", i.e. the in-process cache is cold after every scale-to-zero. — [Billing in Azure Container Apps](https://learn.microsoft.com/azure/container-apps/billing#consumption-plan)

### Inferences
- Trade-offs text for the doc: "Redirect lookups are cached in-process (HybridCache, L1 only) with a short TTL and stampede protection. This is correct for a single replica and for N replicas that tolerate per-replica warm-up; it is incorrect if links can be edited/deleted and all replicas must see the change within the TTL. The upgrade path is to register an IDistributedCache (Azure Managed Redis) as L2 with no code change to callers. Redis was not provisioned because the reviewer must run locally without a subscription, Azure Cache for Redis is being retired, and Managed Redis has no free tier."
- Use HybridCache over raw IMemoryCache even for L1-only because the API is the same one you would use with Redis later, and because stampede protection is a talking point. If the engineer prefers fewer moving parts, IMemoryCache is equally defensible and is what Microsoft itself says is "sufficient" for single-server simple caching.
- Caching makes the Azure SQL free-offer auto-pause story better (fewer DB hits), but keep-alive connections from the pool still block auto-pause; mention `Min Pool Size=0` / idle connection lifetime if the prototype goes to Azure.

### Gaps
- No source fetched on Azure Managed Redis pricing or on whether a free/trial SKU exists (UNVERIFIED: none).
- Cache-invalidation requirements depend on whether links are mutable in this assignment; not knowable from the research brief.

## Key Question 5: Analytics storage — same DB table vs separate append-only table vs Azure Table/Blob vs message queue

### Takeaway
For a prototype that must be honest about limits, an append-only `Clicks` table in the same relational database (written fire-and-forget via a bounded in-process channel/background service) is the defensible choice; it keeps the reviewer's local run to one dependency while the ADR records that at scale clicks would move to a queue + columnar/analytics store (the pattern dub.co uses with Tinybird and Sink uses with Cloudflare Analytics Engine).

### Cited Findings
- VERIFIED: dub's README lists Tinybird for analytics, Upstash (Redis) for cache, PlanetScale as database, Prisma as ORM, Next.js/TypeScript, Vercel hosting; it claims to power "100M+ clicks and 2M+ links monthly". — [dubinc/dub](https://github.com/dubinc/dub)
- VERIFIED: Sink uses "Cloudflare D1" as "the authoritative link store", "Workers KV" as "a write-through read cache", "Cloudflare Workers Analytics Engine" for analytics, and optional R2 snapshots. — [ccbikai/Sink](https://github.com/ccbikai/Sink)
- VERIFIED: Azure Table Storage warns that "append-only or prepend-only patterns" on PartitionKey "might limit the throughput of your insert operations" and recommends random/GUID-like keys for hot inserts; single-partition limit about 2,000 entities/sec. — [Design a scalable partitioning strategy](https://learn.microsoft.com/rest/api/storageservices/designing-a-scalable-partitioning-strategy-for-azure-table-storage#choose-the-partitionkey-value)
- VERIFIED: Azure Cosmos DB exposes a change feed "for event-driven architectures (Azure Functions, Spark) & streaming pipelines" and no-ETL analytics via Synapse Link / Fabric mirroring. — [Azure Cosmos DB overview](https://learn.microsoft.com/azure/cosmos-db/overview#for-free)
- UNVERIFIED: Azure Storage Queues / Service Bus Basic as the queue option; Azure Storage account (Blob/Queue/Table) is in the Azure free-account 12-month list and costs pennies thereafter. Azure Service Bus Basic has a per-million-operations price, no free tier. Not fetched.

### Inferences
- Option ranking for the prototype:
  1. Same DB, separate append-only `Clicks(Id bigint identity, ShortCode, OccurredAtUtc, Referrer, UserAgentHash, Country?)` table, indexed on `(ShortCode, OccurredAtUtc)`, written asynchronously via `System.Threading.Channels` + `BackgroundService` so the redirect never waits on the insert. Honest limits to state: write amplification on the primary DB, table growth, the channel is lost on crash (acceptable for analytics), and aggregation queries compete with OLTP.
  2. Counter column on the `Links` row (`UPDATE ... SET ClickCount = ClickCount + 1`) — simplest, but hot-row contention and no dimensional analytics; fine as a supplementary denormalized value.
  3. Azure Table/Blob append — removes load from the relational DB and is nearly free, but introduces a second local dependency (Azurite) for the reviewer and a second data path to test.
  4. Queue + consumer (Storage Queue / Service Bus / Kafka) feeding an analytics store — the "real" production shape (dub/Tinybird, Sink/Analytics Engine) but over-engineering for 2-3 days; document as the roadmap.
- The ADR should state explicitly that analytics writes are at-least-once/best-effort and must never fail or slow the redirect; that is the single most important honesty point reviewers look for.

### Gaps
- No primary sources on Azure Storage Queue / Service Bus pricing or free grants were fetched.
- No evidence gathered on what kutt or shlink do for click analytics specifically (both appear to use their primary relational DB; UNVERIFIED).

## Key Question 7: What well-known reference implementations use

### Takeaway
Every mainstream open-source shortener except Sink is backed by a relational database (MySQL/MariaDB for YOURLS; PlanetScale/MySQL + Prisma for dub; SQLite/Postgres/MySQL for kutt; SQLite/MySQL/MariaDB/Postgres/MSSQL for shlink), with Redis as an optional cache/lock layer and a separate analytics system only at dub's scale (Tinybird). This supports "relational primary store + optional cache + append-only analytics" as the conventional, defensible design.

### Cited Findings
- VERIFIED: dub tech stack (README): Next.js, TypeScript, Tailwind, Prisma (ORM), Upstash (Redis), Tinybird (analytics), PlanetScale (database), NextAuth.js, BoxyHQ, Turborepo, Stripe, Resend, Vercel; repo topics include "mysql". — [dubinc/dub](https://github.com/dubinc/dub)

- VERIFIED: Sink (Nuxt 4 on Cloudflare Workers): D1 as "the authoritative link store", Workers KV as "a write-through read cache", Workers Analytics Engine for analytics, R2 for optional snapshots; Cloudflare Pages deployment is deprecated. — [ccbikai/Sink](https://github.com/ccbikai/Sink)
