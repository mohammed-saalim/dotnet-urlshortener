# .NET 8 / ASP.NET Core 8 / EF Core 8 / Azure technical claims for a URL-shortener prototype

Research date: 2026-10-10. All claims checked against learn.microsoft.com, dotnet.microsoft.com, nuget.org, official GitHub repos or IETF datatracker. Labels: **VERIFIED**, **PARTIALLY VERIFIED**, **REFUTED**, **UNVERIFIED**. Versions and dates are as observed on the pages at research time.

Headline for the report writer: **.NET 8 LTS leaves support on 2026-11-10, one month from today.** A prototype started now on .NET 8 would be on an unsupported runtime within weeks. .NET 10 (LTS, supported to 2028-11-14) is the defensible default; .NET 11 is at RC1 and GAs in November 2026. Many "net8 vs net9/10" deltas below (UseAzureSql, built-in OpenAPI, minimal-API validation, NuGetAuditMode=all, HasIndex on Cosmos) become moot if the engineer targets .NET 10.

---

## 1. ASP.NET Core built-in rate limiting middleware (Microsoft.AspNetCore.RateLimiting)

### Takeaway
VERIFIED: the default rejection status is **503 Service Unavailable**, and the middleware does **not** emit `Retry-After` by default; you set `RejectionStatusCode = 429` and/or an `OnRejected` callback that reads `MetadataName.RetryAfter` off the lease. Four algorithms ship (fixed window, sliding window, token bucket, concurrency). Partitioning by client IP is explicitly flagged as a DoS/spoofing risk and requires `UseForwardedHeaders` with `KnownProxies`/`KnownNetworks` behind a proxy.

### Cited Findings
- **VERIFIED (503 default)** — `RateLimiterOptions.RejectionStatusCode`: "Gets or sets the default status code to set on the response when a request is rejected. Defaults to Status503ServiceUnavailable." Remarks: "This status code will be set before OnRejected is called, so any status code set by OnRejected will 'win' over this default." (API ref, aspnetcore-10.0, same member exists since .NET 7) — [RateLimiterOptions.RejectionStatusCode](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.ratelimiting.ratelimiteroptions.rejectionstatuscode?view=aspnetcore-10.0)
- **VERIFIED (503 default, docs prose)** — "The default rejected status is 503 Service Unavailable." — [Rate limiter samples](https://learn.microsoft.com/aspnet/core/performance/rate-limit-samples?view=aspnetcore-10.0)
- **VERIFIED (Retry-After not set by default)** — Kestrel security-considerations table: `RejectionStatusCode` default 503, "Consider 429 Too Many Requests for public APIs"; `OnRejected` default `null`, described as "Custom rejection handler for adding Retry-After headers or logging." (i.e. Retry-After is something *you* add) — [Kestrel security considerations](https://learn.microsoft.com/aspnet/core/fundamentals/servers/kestrel/security-considerations?view=aspnetcore-10.0#security-middleware)
- **VERIFIED (how to configure 429 + Retry-After)** — Docs show two patterns: (a) `options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;` and (b) `options.OnRejected = async (context, ct) => { if (context.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retryAfter)) context.HttpContext.Response.Headers.RetryAfter = ((int)retryAfter.TotalSeconds).ToString(NumberFormatInfo.InvariantInfo); context.HttpContext.Response.StatusCode = StatusCodes.Status429TooManyRequests; ... }` — [Rate limiting middleware in ASP.NET Core (aspnetcore-8.0 moniker)](https://learn.microsoft.com/aspnet/core/performance/rate-limit?view=aspnetcore-8.0)
- **VERIFIED (RetryAfter metadata availability)** — "`retryAfter` can be used with the TokenBucketRateLimiter, Fixed Window Limiter, and Sliding Window Limiter because these algorithms are able to estimate when more permits are added. The ConcurrencyLimiter has no way of calculating when permits are available." — [Rate limiter samples](https://learn.microsoft.com/aspnet/core/performance/rate-limit-samples?view=aspnetcore-10.0)
- **VERIFIED (algorithms)** — "The RateLimiterOptionsExtensions class provides the following extension methods for rate limiting: Fixed window, Sliding window, Token bucket, Concurrency." `AddFixedWindowLimiter`, `AddSlidingWindowLimiter`, `AddTokenBucketLimiter`, `AddConcurrencyLimiter`; plus `PartitionedRateLimiter.CreateChained` and (named-policy) `RateLimiter.CreateChained`. — [Rate limiting middleware](https://learn.microsoft.com/aspnet/core/performance/rate-limit?view=aspnetcore-8.0)
- **VERIFIED (middleware order)** — "UseRateLimiter must be called after UseRouting when rate limiting endpoint specific APIs are used... When calling only global limiters, UseRateLimiter can be called before UseRouting." — same page.
- **VERIFIED (IP partition pitfall)** — "If you create partitions by using client IP addresses, your app becomes vulnerable to Denial of Service attacks that use IP Source Address Spoofing. For more information, see BCP 38 RFC 2827." Also: "Each distinct key creates and caches its own limiter, so partitioning on unbounded user-controlled input can exhaust memory (a DoS risk)." — same page.
- **VERIFIED (proxy/ForwardedHeaders)** — Recommended order behind a reverse proxy: `app.UseForwardedHeaders(); // MUST come first -- restores client IP/scheme/host` then `UseRateLimiter()`. — [Kestrel security considerations](https://learn.microsoft.com/aspnet/core/fundamentals/servers/kestrel/security-considerations?view=aspnetcore-10.0#security-middleware)
- **VERIFIED (ForwardedHeaders defaults/gotchas)** — Default `ForwardedHeaders` is `None` (must opt in to `XForwardedFor | XForwardedProto`); default `KnownProxies` = `IPv6Loopback` only and `KnownNetworks` = loopback/8 only; "The request's original remote IP must match an entry in the KnownProxies or KnownNetworks lists before forwarded headers are processed"; `ForwardLimit` default 1 (rightmost value only); `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` "uses settings designed for cloud environments and doesn't enable features such as the KnownProxies option." — [Configure ASP.NET Core to work with proxy servers and load balancers](https://learn.microsoft.com/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0)
- **VERIFIED (GitHub history of 503 complaint)** — dotnet/aspnetcore issue #22906 "ConcurrencyLimiter middleware returns 503 when queue is full; would expect 429" (the older ConcurrencyLimiter middleware; same 503 default carried into the .NET 7+ rate limiter). — [dotnet/aspnetcore #22906](https://github.com/dotnet/aspnetcore/issues/22906)
- **VERIFIED (token bucket timer nuance)** — "Constructing a TokenBucketRateLimiter directly with AutoReplenishment set to true gives each limiter instance its own timer. The AddTokenBucketLimiter and RateLimitPartition.GetTokenBucketLimiter helpers instead set AutoReplenishment to false and replenish all of their limiters from a single shared timer." — [Rate limiting middleware](https://learn.microsoft.com/aspnet/core/performance/rate-limit?view=aspnetcore-8.0)

### Inferences
- The behavior (503 default, no Retry-After) is identical across .NET 7/8/9/10; the docs page carries a single moniker range `aspnetcore-7.0 ... aspnetcore-12.0`, so no version delta to flag.
- For a URL shortener on Azure Container Apps / App Service (both terminate TLS at a proxy), `httpContext.Connection.RemoteIpAddress` will be the proxy IP unless `UseForwardedHeaders` runs first with `XForwardedFor` enabled and the proxy range added to `KnownNetworks` (or `KnownProxies`/`KnownNetworks` cleared, which the Entra proxy guide shows but which widens spoofing exposure).
- Use `OnRejected` rather than only `RejectionStatusCode` if you want `Retry-After` + a ProblemDetails body; with fixed/sliding/token-bucket limiters the lease carries `MetadataName.RetryAfter`.

### Gaps
- No official statement found on whether Microsoft plans to change the 503 default in .NET 11; treat as unchanged.

## 2. EF Core Azure Cosmos DB provider limitations (EF Core 8 vs 9 vs 10/11)

### Takeaway
VERIFIED: the Cosmos provider has no migrations, no reverse engineering, no relational-style transactions, and schema concepts (indexes, constraints) are ignored (EF 8) or, for `HasIndex`, throw (EF 9+). Unique constraints are not surfaced through EF at all; Cosmos "unique key policies" can only be set at container creation outside EF. EF 9 also removed synchronous I/O for Cosmos; EF 11 (preview) adds transactional batches and indexing-policy configuration.

### Cited Findings
- **VERIFIED (no relational transactions)** — "Azure Cosmos DB does not provide relational-style transactions or full ACID guarantees across any number of operations and tables. However, the EF Core Azure Cosmos DB provider does use Transactional batches when possible." — [EF Core Azure Cosmos DB Provider Limitations](https://learn.microsoft.com/ef/core/providers/cosmos/limitations)
- **VERIFIED (no migrations)** — "Schema migration is not supported, since there is no defined schema for the documents." — same page.
- **VERIFIED (no scaffolding)** — "Reverse-engineering (scaffolding) a model from an existing database is not supported." — same page.
- **VERIFIED (indexes/constraints ignored)** — "Schema concepts defined on the EF model, like indexes and constraints, are ignored when using a document database, since there is no schema. Note that Azure Cosmos DB NoSQL performs automatic indexing of documents." — same page.
- **VERIFIED (no cross-document Include)** — "Loading graphs of related entities from different documents is not supported." — same page.
- **VERIFIED (EF 9 delta: HasIndex throws)** — Breaking change, low impact: "Previously, calls to HasIndex were ignored by the EF Cosmos DB provider. [New behavior] The provider now throws if HasIndex is specified." (tracking issue #34023) — [Breaking changes in EF Core 9](https://learn.microsoft.com/ef/core/what-is-new/ef-core-9.0/breaking-changes#azure-cosmos-db-breaking-changes)
- **VERIFIED (EF 9 delta: no sync I/O)** — "synchronous EF APIs such as ToList or SaveChanges throw in version 9.0 and above; always use asynchronous methods... Previous versions of EF supported the synchronous APIs by calling .Wait()" (issue #32563) — [Limitations page warning](https://learn.microsoft.com/ef/core/providers/cosmos/limitations)
- **VERIFIED (EF 9 delta: id mapping)** — Key property mapped to JSON `id` by convention and discriminator no longer in `id`; mitigations `HasShadowId()`/`HasShadowIds()`, `HasDiscriminatorInJsonId()`. — [Breaking changes in EF Core 9](https://learn.microsoft.com/ef/core/what-is-new/ef-core-9.0/breaking-changes#azure-cosmos-db-breaking-changes)
- **VERIFIED (EF 9 delta: Take-before-Where throws)** — queries with `Take` before `Where` are no longer translated; exception thrown instead of incorrect results. — same page.
- **VERIFIED (EF 11 preview: transactional batches default)** — "Transactional batches support is being introduced in EF Core 11, which is currently in preview." `AutoTransactionBehavior` Auto (default) / Never (pre-11 behaviour) / Always; limits: single partition, max 100 operations, 2 MB. — [Saving Data with the EF Core Azure Cosmos DB Provider](https://learn.microsoft.com/ef/core/providers/cosmos/saving#transactionality-and-transactional-batches)
- **VERIFIED (EF 11 preview: indexing policy)** — "EF Core 11 adds support for more Azure Cosmos DB indexing policy configuration. You can now disable automatic indexing, exclude individual paths... and emit explicit single-property, composite, vector, and full-text indexes" — [What's New in EF Core 11](https://learn.microsoft.com/ef/core/what-is-new/ef-core-11.0/whatsnew#cosmos-db)
- **VERIFIED (Cosmos unique keys are a container-creation-time concept)** — "You can define unique keys only when you create an Azure Cosmos DB container. A unique key is scoped to a logical partition... You can't update an existing container to use a different unique key." — [Unique key constraints in Azure Cosmos DB](https://learn.microsoft.com/azure/cosmos-db/unique-keys#define-a-unique-key)

### Inferences
- For a URL shortener's "short code must be unique" invariant, EF Core on Cosmos gives you nothing: `HasIndex(...).IsUnique()` is ignored (EF 8) or throws (EF 9/10). Uniqueness must come from making the short code the document `id` within a partition (Cosmos enforces `id` uniqueness per logical partition) or from a unique key policy created via the Cosmos SDK/ARM/Bicep, not via EF.
- Azure SQL with EF Core SQL Server provider (migrations, unique indexes, transactions all supported) is the simpler fit for the prototype; Cosmos adds provider caveats without a benefit at prototype scale.

### Gaps
- No EF Core API documented for configuring Cosmos unique key policies; EF docs are silent, so this is inferred from the Cosmos service docs rather than stated by EF docs.

## 3. `UseAzureSql()` / `UseAzureSynapse()` vs `UseSqlServer()` + `EnableRetryOnFailure`

### Takeaway
VERIFIED: `UseAzureSql` and `UseAzureSynapse` were introduced in **EF Core 9.0** (not 10). The claim "EF Core 9/10" is therefore half right. On EF Core 8 use `UseSqlServer(conn, o => o.EnableRetryOnFailure())`; `EnableRetryOnFailure` has existed since EF Core 1.1 and is present in EF Core 8.0.

### Cited Findings
- **VERIFIED (introduced in EF 9)** — "UseAzureSql was introduced in EF Core 9.0. When using an older version, use UseSqlServer instead." and identically for UseAzureSynapse. — [Microsoft SQL Server EF Core Database Provider](https://learn.microsoft.com/ef/core/providers/sql-server/#usage-and-configuration)
- **VERIFIED (EF 9 what's new)** — "Instead of configuring EF with UseSqlServer, you can now specify UseAzureSql or UseAzureSynapse. This allows EF to produce better SQL when using Azure SQL or Azure Synapse." — [What's New in EF Core 9](https://learn.microsoft.com/ef/core/what-is-new/ef-core-9.0/whatsnew#linq-and-sql-translation)
- **VERIFIED (resiliency auto-configured with UseAzureSql)** — "When using UseAzureSql and UseAzureSynapse, connection resiliency is automatically set up with the appropriate settings specific for those databases. Otherwise, when using UseSqlServer, configure the provider with EnableRetryOnFailure... Starting with EF 9... call `ConfigureSqlEngine(c => c.EnableRetryOnFailureByDefault())`" — [SQL Server provider: connection resiliency](https://learn.microsoft.com/ef/core/providers/sql-server/#connection-resiliency)
- **VERIFIED (EnableRetryOnFailure exists in EF Core 8)** — API reference lists `Microsoft.EntityFrameworkCore.SqlServer v8.0.0` among "Applies to" (also v1.1.6 through v10.0.0). Defaults: "6 for the maximum retry count and 30 seconds for the maximum default delay". Overloads: `()`, `(int maxRetryCount)`, `(ICollection<int> errorNumbersToAdd)`, `(int, TimeSpan, IEnumerable<int>?)`. — [SqlServerDbContextOptionsBuilder.EnableRetryOnFailure (efcore-8.0)](https://learn.microsoft.com/en-us/dotnet/api/microsoft.entityframeworkcore.infrastructure.sqlserverdbcontextoptionsbuilder.enableretryonfailure?view=efcore-8.0)
- **VERIFIED (EF 10 delta)** — With `UseAzureSql` or compatibility level 170+, EF 10 defaults JSON columns to the new native `json` type; existing `nvarchar(max)` JSON columns "will be automatically changed to json with the first migration" unless opted out. — [What's New in EF Core 10](https://learn.microsoft.com/ef/core/what-is-new/ef-core-10.0/whatsnew#azure-sql-and-sql-server)
- **VERIFIED (supported engines)** — "Microsoft SQL Server (2019 onwards), Azure SQL Database, Azure Synapse Analytics". — [SQL Server provider](https://learn.microsoft.com/ef/core/providers/sql-server/#connection-resiliency)

### Inferences
- EF Core 8 code: `options.UseSqlServer(cs, sql => sql.EnableRetryOnFailure())`. EF Core 9/10 code: `options.UseAzureSql(cs)` (retry is implicit). If the engineer moves to .NET 10 / EF 10, `UseAzureSql` is the idiomatic call, but be aware of the automatic `json` column type migration.

### Gaps
- None.

## 4. Microsoft.Extensions.Caching.Hybrid (HybridCache): GA, versions, .NET 8 support

### Takeaway
VERIFIED: HybridCache reached GA with package **9.3.0 on 2025-03-11**; latest stable observed is **10.10.0 (2026-09-09)**. It runs on .NET 8 (package targets net8.0/net9.0/net10.0, netstandard2.0/2.1, net462+; docs say it supports ".NET Framework 4.7.2 and .NET Standard 2.0"). Versus IMemoryCache + IDistributedCache it adds stampede protection, L1/L2 in one API, tag invalidation and configurable serialization.

### Cited Findings
- **VERIFIED (GA announcement)** — .NET Blog post "Hello HybridCache! Streamlining Cache Management for ASP.NET Core Applications" (URL slug `hybrid-cache-is-now-ga`), and NuGet version 9.3.0 "last updated on 3/11/2025". — [devblogs.microsoft.com: HybridCache is now GA](https://devblogs.microsoft.com/dotnet/hybrid-cache-is-now-ga/); [NuGet 9.3.0](https://www.nuget.org/packages/Microsoft.Extensions.Caching.Hybrid/9.3.0)
- **PARTIALLY VERIFIED (latest version / TFMs)** — NuGet page as fetched: latest stable 10.10.0 (2026-09-09); frameworks listed .NET 8.0, 9.0, 10.0; .NET Standard 2.0 and 2.1; .NET Framework 4.6.2+. The fetch also claimed "earliest GA 10.0.0 (2025-11-11)", which conflicts with the 9.3.0 GA evidence above; the 9.3.0 blog/NuGet evidence is treated as authoritative, the parser likely only saw the 10.x version list. — [NuGet Microsoft.Extensions.Caching.Hybrid](https://www.nuget.org/packages/Microsoft.Extensions.Caching.Hybrid)
- **VERIFIED (older runtime support)** — "The HybridCache library supports older .NET runtimes, down to .NET Framework 4.7.2 and .NET Standard 2.0." — [HybridCache library in ASP.NET Core](https://learn.microsoft.com/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0#compatibility)
- **VERIFIED (features vs IMemoryCache/IDistributedCache)** — Unified L1 (MemoryCache) + optional L2 (any `IDistributedCache`), "Stampede protection... ensures that only one concurrent caller for a given key calls the factory method", configurable serializers, tag-based invalidation (`RemoveByTagAsync`, logical not physical), defaults `MaximumPayloadBytes` 1 MB and `MaximumKeyLength` 1024. — [Overview of caching: HybridCache](https://learn.microsoft.com/aspnet/core/performance/caching/overview?view=aspnetcore-10.0#hybridcache); [HybridCache library](https://learn.microsoft.com/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0)
- **VERIFIED (gotcha: AddDistributedMemoryCache is ignored as L2)** — "When the primary cache is the default MemoryCache, HybridCache doesn't use the IDistributedCache implementation registered by AddDistributedMemoryCache as its secondary cache... If it's the only IDistributedCache registered, HybridCache caches in-process only." — [HybridCache library: Cache storage](https://learn.microsoft.com/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0#cache-storage)
- **VERIFIED (gotcha: cross-instance invalidation)** — "When invalidating cache entries by key or by tags, they're invalidated in the current server and in the secondary out-of-process storage. However, the in-memory cache in other servers isn't affected." — same page.
- **VERIFIED (stampede scope)** — "This coordination doesn't extend to other HybridCache instances, even if they use the same secondary distributed cache." — same page.
- **VERIFIED (plain IMemoryCache/IDistributedCache still documented)** — .NET caching overview lists three approaches: `Microsoft.Extensions.Caching.Memory`, `Microsoft.Extensions.Caching.Hybrid`, `Microsoft.Extensions.Caching.Distributed`. — [Caching in .NET](https://learn.microsoft.com/dotnet/core/extensions/caching)
- **VERIFIED (pre-GA confusion context)** — dotnet/aspnetcore issue #59702 "Why is HybridCache Still in Preview After .NET 9 Release?" (Nov 2024); GA shipped out-of-band in March 2025. — [dotnet/aspnetcore #59702](https://github.com/dotnet/aspnetcore/issues/59702)

### Inferences
- For a single-instance prototype, `AddHybridCache()` with no L2 gives in-process caching plus stampede protection with less code than a hand-rolled `IMemoryCache.GetOrCreateAsync` cache-aside; it is a NuGet package, not part of the .NET 8 shared framework, so add `Microsoft.Extensions.Caching.Hybrid` explicitly. The 9.x line works on net8.0; 10.x line also lists net8.0.
- If horizontal scale-out is in scope, note that redirect-cache invalidation (e.g., on short-link delete) only clears the local L1 and the L2, not other replicas' L1; use short `LocalCacheExpiration`.

### Gaps
- Could not confirm from the NuGet fetch which 10.x versions still target net8.0 after .NET 8 EOL (2026-11-10); the fetched TFM list includes net8.0 as of 10.10.0.

## 5. Passwordless auth to Azure SQL: `Authentication=Active Directory Default` / DefaultAzureCredential

### Takeaway
VERIFIED: `Active Directory Default` (SqlClient 3.0+) uses the Azure Identity `DefaultAzureCredential` chain and works both locally (Visual Studio / Azure CLI / Azure PowerShell / azd sign-in) and in App Service / Container Apps via managed identity with no code change. Gotchas: slow first connection, `User Id=<client-id>` for user-assigned identity, DB-side user/role must be created, and **SqlClient 6.0+/7.x moved the Entra providers into the separate `Microsoft.Data.SqlClient.Extensions.Azure` package** (affects .NET 11; EF Core 8/10 still pull SqlClient 5.x).

### Cited Findings
- **VERIFIED (works local + App Service)** — "You can use Active Directory Default authentication both on your local machine and in Azure App Service. The driver can acquire a token from Microsoft Entra ID in several different ways. If the app is deployed, the driver gets a token from the app's system-assigned managed identity. The driver can also authenticate with a user-assigned managed identity if you include `User Id=<client-id-of-user-assigned-managed-identity>;` in your connection string." — [Tutorial: Use managed identity to connect an Azure web app to Azure SQL](https://learn.microsoft.com/azure/app-service/tutorial-connect-msi-sql-database#modify-your-project-and-publish-your-app)
- **VERIFIED (connection string form)** — `Server=tcp:<server>.database.windows.net,1433;Initial Catalog=<db>;Encrypt=True;TrustServerCertificate=False;Connection Timeout=30;Authentication="Active Directory Default";` and "Passwordless connection strings are safe to commit to source control". — [Connect to and query Azure SQL Database using .NET](https://learn.microsoft.com/azure/azure-sql/database/azure-sql-dotnet-quickstart?view=azuresql#configure-the-connection-string)
- **VERIFIED (credential chain)** — "Candidates depend on the installed Azure Identity version and configuration. They include environment credentials, workload identity, managed identity, and signed-in development tools such as Visual Studio, Azure CLI, Azure PowerShell, and Azure Developer CLI." "SqlClient disables InteractiveBrowserCredential in this mode." — [Microsoft Entra authentication with Microsoft.Data.SqlClient](https://learn.microsoft.com/sql/connect/ado-net/sql/azure-active-directory-authentication?view=sql-server-ver17#use-default-authentication)
- **VERIFIED (gotcha: slow first connection; prefer explicit mode in prod)** — "Active Directory Default can make the first connection slow because DefaultAzureCredential tries credential providers in sequence... Prefer a specific authentication mode in production, such as Active Directory Managed Identity..." — same page.
- **VERIFIED (minimum driver versions)** — `Active Directory Default` first supported in SqlClient **3.0**; `Active Directory Managed Identity` in 2.1; Workload Identity in 5.2; azd credential in the Default chain from 5.1.4. — same page, "Choose an authentication mode" table.
- **VERIFIED (gotcha: separate Azure extension package in SqlClient 6+/7+)** — "Microsoft.Data.SqlClient 7.0 and later versions require the version-matched Microsoft.Data.SqlClient.Extensions.Azure package for driver-provided Microsoft Entra ID authentication modes." — [Connection strings for Microsoft.Data.SqlClient](https://learn.microsoft.com/sql/connect/ado-net/connection-strings?view=sql-server-ver17#choose-an-authentication-pattern); ASP.NET Core 11 breaking change: ".NET 10 [transitively uses SqlClient] 5.x... Starting in Microsoft.Data.SqlClient 6.0, the Microsoft Entra ID authentication providers are no longer in the main package" and runtime error `Cannot find an authentication provider for 'ActiveDirectoryDefault'`. — [SqlClient Active Directory authentication moved to a separate package](https://learn.microsoft.com/aspnet/core/breaking-changes/11/sqlclient-azure-extensions-required?view=aspnetcore-10.0)
- **VERIFIED (DB-side setup required)** — "Grant the application or user identity access to the intended database. Obtaining a token doesn't grant database permissions." — [Microsoft Entra authentication with SqlClient: Overview](https://learn.microsoft.com/sql/connect/ado-net/sql/azure-active-directory-authentication?view=sql-server-ver17)
- **VERIFIED (propagation delay)** — "it can take several minutes for changes to Azure users and roles to propagate through your Azure environment." — [Migrate a .NET application to use passwordless connections](https://learn.microsoft.com/azure/azure-sql/database/azure-sql-passwordless-migration?view=azuresql#configure-your-local-development-environment)
- **VERIFIED (Container Apps covered by Service Connector/managed identity)** — "Service Connector enables managed identities in app hosting services like Azure App Service and Azure Container Apps." — [Passwordless connections for Azure services](https://learn.microsoft.com/azure/developer/intro/passwordless-overview#passwordless-connections-and-zero-trust)
- **VERIFIED (user-assigned MI in connection string)** — `Authentication=Active Directory Managed Identity;User Id=<client_id>`; "When migrating from SqlClient 2.1, replace the user-assigned identity's object ID with its client ID. SqlClient uses the client ID starting with 3.0." — [SqlClient Entra auth: managed identity](https://learn.microsoft.com/sql/connect/ado-net/sql/azure-active-directory-authentication?view=sql-server-ver17#use-device-code-flow-authentication)

### Inferences
- On .NET 8 + EF Core 8 the transitive SqlClient is 5.1.x, which includes Entra providers, so `Active Directory Default` works with no extra package. If the engineer pins a newer `Microsoft.Data.SqlClient` (6.x/7.x) directly, they must also add `Microsoft.Data.SqlClient.Extensions.Azure`.
- Local dev: run `az login` (or sign in to VS/azd) with a user that has been created in the DB (`CREATE USER [user@tenant] FROM EXTERNAL PROVIDER`), or the connection fails with login errors unrelated to the token.
- Container Apps: use `Active Directory Managed Identity` (or Default) with the system-assigned identity; for user-assigned, pass `User Id=<client id>`.

### Gaps
- No Container-Apps-specific SqlClient tutorial found in the sources fetched; Container Apps support is inferred from the generic managed-identity + Service Connector docs rather than a dedicated SqlClient page.

## 6. .NET support dates as of October 2026: is .NET 8 still defensible?

### Takeaway
VERIFIED with exact dates: **.NET 8 LTS support ends 2026-11-10** (one month from research date); .NET 9 STS also ends 2026-11-10; **.NET 10 LTS (released 2025-11-11) is supported until 2028-11-14**; .NET 11 RC1 (go-live) shipped 2026-09-08 and GA is expected November 2026. A new prototype should target .NET 10, not .NET 8.

### Cited Findings
- **VERIFIED (exact dates, official policy page)** — .NET 10 LTS: released 2025-11-11, latest patch 10.0.12 (2026-09-08), end of support **2028-11-14**. .NET 9 STS: released 2024-11-12, latest 9.0.20, end of support **2026-11-10**. .NET 8 LTS: released 2023-11-14, latest 8.0.31, end of support **2026-11-10**. ".NET 11 RC1 was released September 8, 2026 with end of support October 13, 2026 (go-live release)." — [.NET Support Policy (dotnet.microsoft.com)](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)
- **VERIFIED (corroboration)** — "10.0 (LTS)—Support ends November 14, 2028. 9.0 (STS)—Support ends November 10, 2026. 8.0 (LTS)—Support ends November 10, 2026." — [Install .NET SDK with Snap: .NET releases](https://learn.microsoft.com/dotnet/core/install/linux-snap-sdk#net-releases)
- **VERIFIED (policy definitions)** — LTS "supported for a minimum of three years, or one year after the next LTS release ships if that date is later"; STS "supported for two years (24 months)". Even-numbered = LTS, odd = STS; major releases ship annually in November. — [Releases and support for .NET](https://learn.microsoft.com/dotnet/core/releases-and-support#net-version-lifecycles); [Lifecycle FAQ - .NET](https://learn.microsoft.com/lifecycle/faq/dotnet-core)

## 7. Testing stack: xUnit + WebApplicationFactory, Testcontainers.MsSql, SQLite in-memory as EF Core test double

### Takeaway

### Cited Findings

- **VERIFIED (SQLite vs SQL Server differences, documented)** — "testing against SQLite does not guarantee the same results as against SQL Server... (2) Some queries which work on SQL Server simply aren't supported on SQLite... (4) Raw SQL may work, or it may fail or return different results". — [Choosing a testing strategy](https://learn.microsoft.com/ef/core/testing/choosing-a-testing-strategy#different-types-of-test-doubles)

- **VERIFIED (SQLite in-memory connection lifetime gotcha)** — "a new database is created whenever a low-level connection is opened, and that it's deleted when that connection is closed... we open the connection before passing it to EF Core, and arrange for it to be closed only when the test completes" — [Testing without your production database system: SQLite in-memory](https://learn.microsoft.com/ef/core/testing/testing-without-the-database#repository-pattern)
- **VERIFIED (InMemory provider does not enforce unique indexes)** — "you might add a unique index on a column in your EF Core model and write a test against your in-memory database to check that it does not let you add a duplicate value. ### Inferences
- For a URL shortener where the key correctness property is "duplicate short code is rejected by a unique index", the InMemory provider cannot test it, SQLite can (SQLite enforces UNIQUE), but case-sensitivity differs: a SQL Server `nvarchar` unique index is case-insensitive by default collation, SQLite's is case-sensitive, so a test for `abc` vs `ABC` collision passes on SQL Server and fails on SQLite. ## 9. System.Threading.Channels bounded channel + BackgroundService for async click analytics

### Takeaway
VERIFIED: `Channel.CreateBounded<T>(new BoundedChannelOptions(n) { FullMode = ... })` with `BoundedChannelFullMode` values Wait (default), DropNewest, DropOldest, DropWrite. `HostOptions.ShutdownTimeout` defaults to 30 seconds. Since .NET 6, an unhandled exception in `BackgroundService.ExecuteAsync` stops the host (`BackgroundServiceExceptionBehavior.StopHost` default); .NET 11 further makes `RunAsync` fault (non-zero exit) in that case.

### Cited Findings
- **VERIFIED (BoundedChannelFullMode values)** — `Wait = 0` "Waits for space to be available"; `DropNewest = 1` "Removes and ignores the newest item in the channel"; `DropOldest = 2` "Removes and ignores the oldest item"; `DropWrite = 3` "Drops the item being written." — [BoundedChannelFullMode Enum](https://learn.microsoft.com/dotnet/api/system.threading.channels.boundedchannelfullmode?view=net-11.0-pp)
- **VERIFIED (default bounded behavior)** — "When the bound is reached, the default behavior is that the channel asynchronously blocks the producer until space becomes available." Channels throw `ChannelClosedException` when used after being closed. — [System.Threading.Channels library](https://learn.microsoft.com/dotnet/core/extensions/channels#bounding-strategies)
- **VERIFIED (ShutdownTimeout default 30s)** — "To extend the default 30 second shutdown timeout, set ShutdownTimeout when using Generic Host"; "Hosted service instances stop in the reverse order that they're registered... unless the app opts into concurrent shutdown behavior by setting ServicesStopConcurrently to true"; "If the app shuts down unexpectedly... StopAsync might not be called." — [Background tasks with hosted services in ASP.NET Core](https://learn.microsoft.com/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0#ihostedservice-interface); [HostOptions.ShutdownTimeout](https://learn.microsoft.com/dotnet/api/microsoft.extensions.hosting.hostoptions.shutdowntimeout?view=net-11.0-pp)
- **VERIFIED (BackgroundServiceExceptionBehavior default StopHost)** — "Gets or sets the behavior the IHost will follow when any of its BackgroundService instances throw an unhandled exception. The default is StopHost." — [HostOptions.BackgroundServiceExceptionBehavior](https://learn.microsoft.com/dotnet/api/microsoft.extensions.hosting.hostoptions.backgroundserviceexceptionbehavior?view=net-11.0-pp)
- **VERIFIED (.NET 6 breaking change origin)** — "Unhandled exceptions from a BackgroundService" (.NET 6): to keep the pre-6 behavior set `hostOptions.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.Ignore`. — [Unhandled exceptions from a BackgroundService](https://learn.microsoft.com/dotnet/core/compatibility/core-libraries/6.0/hosting-exception-handling#recommended-action)
- **VERIFIED (.NET 11 delta)** — "In .NET 11, the tasks returned from RunAsync, StopAsync, WaitForShutdownAsync... now fail with an exception instead of completing successfully" when a BackgroundService fails under StopHost; "The application typically exits with a failure exit code (non-zero)." Introduced .NET 11 Preview 3. — [IHost.RunAsync and IHost.StopAsync throw when a BackgroundService fails](https://learn.microsoft.com/dotnet/core/compatibility/extensions/11/ihost-runasync-stopasync-throw-backgroundservice-failure)

### Inferences
- For click analytics, `DropWrite` (or `DropOldest`) is the correct `FullMode`: the redirect hot path must never block on analytics back-pressure; `Wait` (default) would stall redirects when the DB writer falls behind.
- Wrap the consumer loop in try/catch per item; an unhandled exception in `ExecuteAsync` takes the whole web host down under the default `StopHost` (.NET 6-10), and from .NET 11 also surfaces as a faulted `RunAsync`.
- Graceful shutdown: on `StoppingToken`, complete the writer (`channel.Writer.TryComplete()`) and drain remaining items within the 30 s `ShutdownTimeout` (Container Apps / App Service send SIGTERM then kill; the host timeout must be shorter than the platform's grace period). Note `ShutdownTimeout` is a .NET-side cap; exact platform grace periods were not researched here.

### Gaps
- Container Apps / App Service SIGTERM grace period values were not verified in this pass.

### Inferences
- On .NET 8: minimal APIs + Swashbuckle (template default) or `Microsoft.AspNetCore.OpenApi` 8.x `WithOpenApi()` metadata + Swashbuckle UI; validation via an `IEndpointFilter` that runs DataAnnotations `Validator.TryValidateObject` or a third-party library (FluentValidation, MiniValidation) and returns `TypedResults.ValidationProblem(...)`. Controllers on .NET 8 get `[ApiController]` automatic model validation for free, which is the one concrete functional advantage controllers hold over minimal APIs on .NET 8; that gap closes in .NET 10.
- On .NET 10: `AddOpenApi()` + `AddValidation()` + `AddProblemDetails()` + `TypedResults` gives a complete minimal-API story with no third-party packages (except a UI such as Scalar/Swagger UI for the OpenAPI document).
